PYX Gate · API v1

Documentação da API

Crie cobranças Pix e cartão, receba confirmação em tempo real por webhook e gerencie tudo com chaves de API — sem sair do seu próprio sistema.

Introdução

Toda a API pública vive sob o prefixo /v1, separado do painel interno da PYX Gate. Autenticação é feita por chave de API, não por login de usuário.

AmbienteBase URL
Produçãohttps://pyxgate-api.onrender.com/v1

Domínio próprio (api.pyxgate.com) ainda não configurado — use a URL acima até lá. http://localhost:3000/v1 só existe se você estiver rodando o backend localmente pra contribuir com o código da PYX Gate; não é um ambiente de teste pra integradores.

Modo teste vs. produção — não existe sandbox separado

Cada chave de API tem um modo, mas a URL é a mesma nos dois casos — não há um domínio de sandbox à parte. Uma chave sk_test_... roda inteiramente em modo teste na própria API de produção: nunca chama uma adquirente real, nunca move dinheiro, nunca aparece nos relatórios financeiros reais. A confirmação de um pagamento em modo teste é manual, via os endpoints de simulação. Uma chave sk_live_..., na mesma URL, processa pagamentos reais.

Pagamentos, listagens e consultas são sempre escopados ao modo da chave usada — uma chave de teste nunca enxerga pagamentos reais, e vice-versa. Pra testar sua integração de ponta a ponta, gere uma chave sk_test_... no dashboard e siga o fluxo de simulação.

Convenção de valores

Valores monetários são sempre inteiros em centavos (amount: 1990 = R$ 19,90). IDs de recursos têm prefixo por tipo: pay_..., we_..., evt_....

Autenticação

PrefixoTipoOnde usar
sk_live_... / sk_test_...Secret keySó no seu backend. Autoriza todas as operações.
pk_live_... / pk_test_...Publishable keyPode aparecer em frontend. Hoje não autentica endpoints de /v1 — reservada para SDKs client-side futuros.
Nunca exponha sua secret key

Não coloque uma sk_... em código de frontend, app mobile ou repositório público. Se acontecer, revogue no dashboard imediatamente e gere outra.

Envie a chave no header Authorization:

# requisições sem chave, com chave inválida ou revogada recebem 401
curl https://pyxgate-api.onrender.com/v1/account \
  -H "Authorization: Bearer sk_test_51H8x..."

Gerando, revogando e rotacionando

No dashboard, em Desenvolvedores: crie uma chave (nome, tipo, modo) — ela só é exibida completa uma vez. Revogar invalida a chave imediatamente e não pode ser desfeito. Rotacionar cria uma chave nova e revoga a antiga na mesma operação — use quando suspeitar de vazamento.

Idempotência

Envie um valor único por operação no header Idempotency-Key em requisições POST. Reenviar a mesma requisição (retry por timeout, rede instável) com a mesma chave e o mesmo corpo retorna a resposta original, sem duplicar a cobrança.

Mesma chave + mesmo payloadRetorna a resposta já registrada, sem reprocessar.
Mesma chave + payload diferente400 idempotency_key_reused.
TTL24 horas — depois disso a chave pode ser reutilizada livremente.

Suportado hoje em POST /v1/payments. Use um identificador que já existe no seu sistema (ID do pedido) em vez de um UUID aleatório a cada tentativa.

Verificando a assinatura

Toda entrega inclui o header PYX-Signature: t=<timestamp>,v1=<hmac>, onde v1 é HMAC-SHA256(secret, "{t}.{corpo_bruto}"). Sempre verifique antes de confiar no payload.

const crypto = require("crypto");

function verifyPyxSignature(rawBody, signatureHeader, secret) {
  const [tPart, v1Part] = signatureHeader.split(",");
  const timestamp = tPart.split("=")[1];
  const received = v1Part.split("=")[1];

  const expected = crypto
    .createHmac("sha256", secret)
    .update(`${timestamp}.${rawBody}`)
    .digest("hex");

  const a = Buffer.from(expected, "hex");
  const b = Buffer.from(received, "hex");
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
function verifyPyxSignature(string $rawBody, string $signatureHeader, string $secret): bool {
    $parts = [];
    foreach (explode(",", $signatureHeader) as $part) {
        [$key, $value] = explode("=", $part, 2);
        $parts[$key] = $value;
    }

    $timestamp = $parts["t"] ?? "";
    $received = $parts["v1"] ?? "";
    $expected = hash_hmac("sha256", "{$timestamp}.{$rawBody}", $secret);

    return hash_equals($expected, $received);
}
Retentativas

Se seu endpoint não responder 2xx, a entrega é tentada novamente (imediata, +10s, +1min, +5min — 4 tentativas). Responda 200 rápido e processe de forma assíncrona se sua lógica for demorada.

Guia: Pix, do zero ao pedido liberado

1. Gere uma chave de teste no dashboard. 2. Crie a cobrança. 3. Exiba qr_code_base64 (imagem) e qr_code (copia-e-cola). 4. Cadastre um webhook para payment.paid. 5. Simule a confirmação. 6. Consulte o pagamento e confirme status: "paid". 7. No handler do webhook (depois de verificar a assinatura), libere o pedido usando o order_id que você mandou em metadata.

Em produção, o passo 5 não existe — o status muda sozinho quando o Pix é pago de verdade, e você só precisa reagir ao webhook.

Guia: Cartão

Leia antes de integrar

1. PCI: número, validade e CVV trafegam direto no corpo da sua requisição para POST /v1/payments — isso coloca você no escopo de responsabilidade PCI-DSS equivalente a manipular dados de cartão diretamente. Não há tokenização client-side hoje.

2. Token 3DS exposto no navegador: o fluxo abaixo expõe no navegador do seu comprador o mesmo token que autentica toda a comunicação da PYX Gate com a Zendry (não escopado só pra 3DS) — é assim que o SDK oficial deles funciona.

Só funciona para sellers com adquirente Zendry.

1. Pegue o token (seu backend)

curl https://pyxgate-api.onrender.com/v1/card_authentications/token \
  -H "Authorization: Bearer sk_live_..."

2. Rode o desafio 3DS (navegador do comprador)

Carregue https://cdn.zendry.com/v1/zendry-sdk-threeds.min.js e chame:

ZendrySDKThreeds.init_threeds({
  token: tokenDoServidor, // obtido no passo 1
  amount: 1990, // centavos, mesmo valor da cobrança
  payment_form: {
    pan: "4242424242424242",
    expiry_month: "12",
    expiry_year: "29", // 2 dígitos! "2029" é rejeitado
    card_holder_name: "MARIA COMPRADORA",
    account_type: "CREDIT", // ou "DEBIT"
    network_preference: "VISA", // VISA | MASTERCARD | AMEX | ELO | DINERS | CB
  },
  onSuccess: (result) => { /* result.three_ds_data */ },
  onFailure: (result) => { /* desafio recusado */ },
  onError: (error) => { /* erro técnico */ },
});

O SDK cria a sessão 3DS e roda o desafio sozinho — não passa pelo backend da PYX Gate. Não cobra nada. onSuccess devolve three_ds_data com 7 dos 13 campos de threeds_data: operation_session_id, xid, eci, cavv, secure_version, directory_server_transaction_id, three_ds_server_transaction_id.

3. Complete com fingerprint do navegador

Os outros 6 campos não vêm do SDK — colete direto:

const threeds_data = {
  ...result.three_ds_data,
  ip_address: ipDoComprador, // obtenha no seu backend
  user_agent_browser_value: navigator.userAgent,
  http_browser_language: navigator.language,
  http_browser_screen_height: String(screen.height),
  http_browser_screen_width: String(screen.width),
  zip_code: cepDeCobranca,
};

4. Cobre de verdade

Envie threeds_data completo em POST /v1/payments com payment_method: "card".

Modo teste

Em sk_test_..., threeds_data ainda é exigido pela validação mas não é verificado de verdade — envie qualquer objeto não vazio. Isso testa o passo 4, não valida se os passos 1–3 do SEU fluxo estão corretos.

Guia: checkout de e-commerce

Fluxo recomendado: seu backend cria o pedido → chama POST /v1/payments (server-side, nunca no navegador do comprador) → exibe o QR code retornado → aguarda o webhook payment.paid → marca o pedido como pago e libera o produto/acesso.

Checklist antes de produção
  • Cobrança criada pelo backend, nunca pelo navegador do comprador.
  • Secret key só em variável de ambiente do servidor.
  • Webhook verifica a assinatura antes de confiar no payload.
  • Quem marca o pedido como pago é o webhook, não o polling do frontend.
  • Handler do webhook é idempotente.
  • Idempotency-Key usado na criação da cobrança.
  • Testado em modo teste de ponta a ponta antes de trocar para chave live.

MCP — conectando agentes de IA

O MCP (Model Context Protocol) é o padrão que permite que um assistente de IA — Claude, Cursor, n8n ou seu próprio agente — use ferramentas externas. O servidor MCP da PYX Gate expõe a API /v1 como ferramentas, para que um agente crie uma cobrança Pix, consulte um pagamento ou cadastre um webhook conversando em português.

Não é uma API nova: é a mesma /v1 desta documentação, com outra embalagem. Tudo que vale aqui vale igual lá — valores em centavos, modo teste isolado, idempotência, escopo por credencial.

Conectando

claude mcp add --transport http pyxgate https://mcp.pyxgate.com/mcp

Na primeira chamada o cliente abre o navegador na tela de autorização da PYX Gate. Você entra com seu login de seller, escolhe o ambiente (teste ou produção) e marca quais permissões concede. Não é preciso criar nem colar chave de API nenhuma.

Onde isso é útil

Integrar seu checkout com a ajuda de um agente de código, deixar o time de suporte consultar pagamentos em linguagem natural, ou automatizar cobranças dentro de um fluxo de agente.

Autorização: OAuth 2.1

O MCP não usa chave de API. Usa OAuth 2.1 com PKCE, seguindo a especificação de autorização do MCP. O motivo é concreto: uma chave sk_ é tudo-ou-nada e vive para sempre num arquivo de configuração. Um agente de IA lê texto de terceiros — e-mails, páginas, planilhas — e por isso precisa de uma credencial de escopo reduzido, com prazo, revogável e presa a um ambiente.

PeçaComo funciona
Descoberta/.well-known/oauth-protected-resource aponta o Authorization Server; /.well-known/oauth-authorization-server lista os endpoints. O cliente acha tudo sozinho.
RegistroDynamic Client Registration (RFC 7591) em POST /oauth/register. Nada para cadastrar à mão.
PKCEObrigatório, só S256. Cliente MCP é público e não guarda segredo.
ConsentimentoTela da PYX Gate: login do seller, escolha de ambiente e checkbox por permissão.
Access tokenJWT assinado em HMAC-SHA256, válido por 1 hora, preso a uma audiência específica.
Refresh token30 dias, uso único com rotação. Guardado só como hash SHA-256.
Revogação em cascataReutilizar um código de autorização ou um refresh token indica vazamento: todas as sessões daquela aplicação caem na hora.

Por que HMAC e SHA-256, e não Argon2

São primitivas para problemas diferentes. Argon2 e bcrypt são KDFs lentas de propósito, feitas para proteger segredo de baixa entropia — senha humana — contra força bruta offline. É por isso que o login de usuário da PYX Gate usa bcrypt, e continua usando.

Um access token ou refresh token nosso tem 256 bits de entropia aleatória: força bruta é inviável por construção. O que se precisa aí é outra coisa — integridade verificável sem ida ao banco (HMAC-SHA256 no access token, validado em memória a cada requisição) e comparação em tempo constante do que está no banco (SHA-256 + timingSafeEqual para código, refresh e client_secret, o mesmo que as chaves sk_ já usam). Argon2 aqui adicionaria dependência nativa e latência por requisição, sem ganhar segurança nenhuma.

O token carrega só o que foi marcado no consentimento. Chamada sem o escopo necessário recebe 403 insufficient_scope.

Conceda escrita em modo teste

Para agentes, conceda payments:write apenas em modo teste, a menos que você realmente queira que o agente crie cobranças reais. O ambiente é escolhido no consentimento e fica gravado no token — não é parâmetro que o agente possa mudar depois.

Cada ferramenta declara anotações (readOnlyHint, destructiveHint) para o cliente MCP saber quando pedir confirmação antes de agir. Chaves sk_ já emitidas continuam funcionando sem mudança: elas carregam escopo *.

Cartão não é exposto como ferramenta

Criar pagamento com cartão exige threeds_data, que só existe depois do desafio 3DS rodar no navegador do comprador (ver guia de cartão). Um agente não tem como produzir esse dado — e uma ferramenta que sempre falha é pior que ferramenta nenhuma.

Rodando o servidor MCP você mesmo

O servidor MCP é um processo separado da API: não tem acesso ao banco nem ao segredo de assinatura, só repassa o token para a /v1. Isso é proposital — comprometer o MCP não compromete o gateway.

cd mcp
npm install

PYXGATE_API_URL=https://pyxgate-api.onrender.com \
MCP_PUBLIC_URL=https://mcp.pyxgate.com/mcp \
PORT=3333 npm start
VariávelOndePara quê
PYXGATE_API_URLMCPBase da API (sem /v1)
MCP_PUBLIC_URLMCPURL pública deste servidor — é a audiência do token
MCP_RESOURCE_URLAPILista (CSV) de recursos aceitos. Precisa conter o MCP_PUBLIC_URL
BASE_URLAPIUsada nos documentos .well-known
O erro mais comum da primeira instalação

MCP_PUBLIC_URL e MCP_RESOURCE_URL divergentes: o token é emitido para um recurso e validado contra outro, e toda chamada volta 401 invalid_token.

Verificando a instalação
